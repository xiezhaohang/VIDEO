# 因果连续性与状态机规则

> 来源：V7.1 人工逐帧复盘。此规则为跨产品通用规则。

## 1. 为什么需要状态机

单个功能镜头“各自成立”并不代表它们可以直接拼进同一时间线。

剪辑前必须持续维护当前世界状态，否则会出现：

- 设备已经安装，却后面又被当成第一次安装
- 手机/手表/耳机在相邻镜头中凭空出现或消失
- 上一个镜头已经完成某功能，下一个镜头又回到准备状态
- 不同独立素材被拼成伪连续过程，造成认知混乱

## 2. 每个候选镜头必须有状态字段

- `state_before`
- `action`
- `state_after`
- `effect_confirmed`
- `new_information`
- `can_follow_previous`
- `causal_conflict`
- `object_presence_before`
- `object_presence_after`
- `orientation_before`
- `orientation_after`

只有 `can_follow_previous=true` 且 `causal_conflict=false` 的镜头，才能作为伪连续时间线直接相邻。

## 3. 状态冲突硬规则

### 已完成动作不得再次作为首次动作

如果时间线中已经出现：

`裸产品 → 吸附手表 → 产品+手表`

后续不能再出现：

`裸产品 → 第一次吸附手表`

除非明确做成“不同场景/不同设备/重复演示”的非连续蒙太奇，并给观众足够的结构分隔。

### 物体不能凭空出现或消失

相邻镜头中如果手机、手表、耳机仓、配件的存在状态发生变化，必须满足至少一种条件：

1. 画面中展示了安装/取下过程；
2. 使用明显不同景别/角度，明确告诉观众这是另一个独立演示；
3. 通过明显转场或结构分段，避免伪装成连续时空。

禁止在近似同构图中直接从“有耳机”切成“无耳机”。

## 4. 功能闭环规则

任何功能段都必须满足：

`操作开始 → 动作完成 → 功能生效 → 成功反馈可见 → 稳定可读 → 安全切出`

### 动作完成不等于功能完成

示例：

- 耳机仓放到充电宝上：动作完成。
- 小黄灯亮起：功能生效。
- 黄灯稳定可见 0.2–0.5 秒：信息闭环。

如果成功反馈没有出现：

- `effect_confirmed=false`
- 不得标记为 Proof
- 可降级为 Demo
- 优先继续向后寻找真实反馈帧

## 5. 核心动作最小时长

核心动作不能按普通 microcut 处理。

必须至少覆盖：

1. 明显靠近/准备
2. 接触/触发
3. 结果出现
4. 稳定尾巴

对于吸附、充电、拿起、亮屏等核心动作：

- 入点不能已经“几乎接触”
- 出点不能在成功反馈刚出现 0.1 秒后立即切走
- 结果出现后通常应保留约 0.3–0.8 秒的人眼可读时间，按真实画面调整

## 6. 独立功能素材的两种合法拼法

### 连续状态型

设备状态必须累积：

`裸产品 → 加手表 → 加手机 → 多设备终态`

### 独立演示蒙太奇型

允许每段从干净状态重新开始，但必须明确让观众知道这是“新的独立功能演示”，不能假装同一连续时空。

方法包括：

- 明显不同角度
- 明显不同景别
- 产品独立重置镜头
- 节奏性硬切但构图差异足够大
- 结构标签/字幕（若项目允许）

## 7. 总编前状态审查

最终时间线生成后，必须逐镜头执行：

1. 比较上一镜头 `state_after` 与下一镜头 `state_before`
2. 检查对象存在状态
3. 检查产品朝向和手势
4. 检查功能是否已经完成过
5. 检查是否出现状态倒退
6. 检查是否出现重复首次动作
7. 检查是否出现弱 proof 覆盖强 proof

任何高严重度冲突必须在 FFmpeg 执行前解决。

## 8. V7.1 验证出的典型错误

- 手机吸附时手表已经安装，后面又再次“首次吸手表”
- 手表成功 proof 后立即凭空消失
- 耳机仓放上去但无成功反馈，之后又凭空消失
- 结尾第三次吸手表，既重复又没有新 proof

这些都不是普通“节奏问题”，而是时间线世界状态没有被维护。
